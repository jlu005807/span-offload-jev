# Jev 路由实验汇总

更新日期：2026-10-28

本文汇总当前已完成的 Jev 路由实验。实验覆盖 90 个 AppWorld 任务的三种输入模式、固定 Span 离线对比、20 个开发任务上的路由器基线比较、四档阈值在线比较，以及对应的失败轨迹分析。各实验的任务集和目标不同，不能把所有百分比当成同一场排行榜。

## 结论先看

- **Jev 已接入并能参与实际路由，但阈值决定了它实际上卸载多少。** 在 90 任务实验中阈值为 0.8，实际交给 SLM 的调用几乎为零；高成功率主要来自 LLM 路径，不能据此证明 Jev 路由准确或省钱。
- **20 个开发任务的四档在线对比中，0.75 是当前较有参考价值的折中点：19/20 成功、22 次 SLM 调用（4.70%）。** 0.8 为 20/20，但只有 3 次 SLM 调用（0.64%）。样本很小，0.75 尚不能称为最佳阈值。
- **低阈值会显著增加 SLM 使用，但成功率没有随阈值降低而稳定提高。** 0.55/0.60/0.65 的成功率分别为 12/20、14/20、12/20；在线分支会改变之后的上下文和执行轨迹，所以阈值变化不只是替换固定的一组调用。
- **目前没有证据证明 Jev 带来净 token 节省或整体成本下降。** 已知 Jev 输入 token 本身就很可观；输出 token、不同模型的实际价格、失败尝试的完整计费和同条件的服务端成本尚不足以计算可靠净收益。

## 实验总览

| 实验 | 规模与目的 | 主要结果 | 可以说明什么 |
|---|---|---|---|
| Jev 三种输入模式全量任务 | 90 个 AppWorld 任务；`context`、`four_features`、`combined`；阈值 0.8 | 成功率分别为 88.89%、92.13%（89 个任务完成）和 94.44%；实际 SLM 调用分别为 5、0、1 | 验证端到端接入和记录；阈值 0.8 下卸载太少，不能比较 Jev 的卸载质量 |
| 固定 Span 三模式推理 | 100 个固定 Span；300 次 Jev 请求；不执行 Agent | 299 次成功；平均 P(SLM)：context 56.03%、four_features 46.01%、combined 53.57% | 比较提示词对模型分数和卸载倾向的影响；不能判断分支正确率或任务收益 |
| 四组在线基线对比 | 同一批 20 个开发任务；原生 LLM、原双门控路由、Jev 0.8、Jev 0.7 | 成功数为 19、6、20、17 | 初步比较实际在线任务表现；小样本且原路由与 Jev 的卸载比例差异很大 |
| 四档 Jev 阈值扫描 | 同一批 20 个开发任务；context 输入；阈值 0.55、0.60、0.65、0.75 | 成功数为 12、14、12、19 | 显示阈值和实际分支选择的关系；用于选后续候选阈值，不足以证明普遍优劣 |
| 0.60 与 0.65 轨迹配对分析 | 对照上述 20 个任务的逐任务结果和调用轨迹 | 两者都成功 9 个；仅 0.60 成功 5 个；仅 0.65 成功 3 个；都失败 3 个 | 解释为何 0.60 在该小样本上比 0.65 多成功 2 个，而非断言 0.60 更好 |

## 一、90 个 AppWorld 任务：三种 Jev 输入模式

三组均使用 OpenJev-1.7B，路由规则为 `P(SLM) >= 0.8` 时卸载，其余使用 LLM。M3 守卫、回滚和 fallback 流程保留；M4 关闭。`four_features` 作业在时间限制内完成 89/90 个任务，因此其成功率按已完成的 89 个计算。

| 输入模式 | 完成任务 | 成功率 | SLM / 总模型调用 | SLM 占比 | 成功响应平均 P(SLM) | 已知 Jev 输入 token | Jev 客户端累计耗时 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `context` | 90/90 | 80/90（88.89%） | 5/1,825 | 0.274% | 54.90% | 4,195,556 | 223.3 秒 |
| `four_features` | 89/90 | 82/89（92.13%） | 0/1,830 | 0% | 44.96% | 约 2.814M | 191.9 秒 |
| `combined` | 90/90 | 85/90（94.44%） | 1/1,837 | 0.054% | 52.06% | 4,116,465 | 222.8 秒 |

说明：`four_features` 的审计重建输入合计为 2,814,356 token；usage 汇总为 2,813,826 token、1,786 条有 usage 的成功响应，二者有 530 token 的记录口径差异。上表取约数，不把它伪装成完全一致的计费值。

### Jev 不可用情况

- `combined`：1,837 次决策中 1,561 次得到有效响应；269 次输入不可用（268 次输入过大、1 次过长）；7 次请求错误（6 次超时、1 次响应无效）。
- `context`：1,825 次决策中 1,702 次有效；121 次输入不可用（102 次字符限制、19 次 token 限制）；2 次请求错误。
- `four_features`：1,830 次决策中 1,787 次有效；25 次输入不可用；18 次请求错误。

不可用时系统走保守的 LLM 路径。它不是 SLM 执行失败后的 rollback/fallback，而是在路由阶段没有拿到 Jev 决策。`combined` 与 `context` 的长输入/预检查不可用较多，是 Jev 覆盖率上的主要问题。

### token 与耗时开销

将已知 Jev **输入** token 加到 Agent 执行模型的输入/输出 token 后：

| 输入模式 | Agent 执行模型 token | 加入已知 Jev 输入后 | token 增幅 | Jev 平均客户端耗时/任务 |
|---|---:|---:|---:|---:|
| `combined` | 33,404,266 | 37,520,731 | 12.32% | 2.48 秒 |
| `four_features` | 33,575,485 | 36,389,311 | 8.38% | 2.16 秒（89 个完成任务） |
| `context` | 34,713,429 | 38,908,985 | 12.09% | 2.48 秒 |

这些是 token 量和客户端时间的观测，不是费用或净节省结论：没有按各模型单价加权，也没有把 Jev 输出 token 算进来；失败请求的实际服务端消耗也未必能由 usage 完整观察。三组全量实验中的 SLM 调用近乎为零，因此执行模型 token 的差异也不能归因于高效卸载。

## 二、固定 Span：提示词影响分数，不代表判断准确

对同一批 100 个 Span 分别构造三种输入，做 300 次 Jev 推理，不运行 Agent，也不调用 SLM 完成步骤。300 次中 299 次获得有效响应；唯一不可用请求发生在 `context` 模式。

| 模式 | 有效响应 | 平均 P(SLM) | 阈值 0.60 下会卸载 | 阈值 0.80 下会卸载 |
|---|---:|---:|---:|---:|
| `context` | 99/100 | 56.03% | 38/100 | 4/100 |
| `four_features` | 100/100 | 46.01% | 5/100 | 0/100 |
| `combined` | 100/100 | 53.57% | 28/100 | 0/100 |

这一实验说明提示词形式会明显改变 Jev 输出的 P(SLM) 分布。由于没有 Span 分支标签、局部正确性标签和净节省标签，它**不能回答哪种模式判断得最准**，也不能把“分数更高”解释为“SLM 更适合”。

## 三、20 个开发任务：原生 LLM、原路由与 Jev 0.8/0.7

四组使用同一批 20 个开发任务。原生 LLM 是全程走大模型；“原路由器”是项目已有的双 Logit 门控；Jev 两组使用 context 输入。

| 组别 | 成功 | SLM / LLM 调用 | SLM 占比 | 已知 Jev 输入 token | 平均 Jev 客户端耗时/任务 |
|---|---:|---:|---:|---:|---:|
| 原生 LLM | 19/20（95%） | 0 / 481 | 0% | — | — |
| 原有双门控路由 | 6/20（30%） | 392 / 107 | 78.56% | — | — |
| Jev 0.8 | 20/20（100%） | 3 / 464 | 0.64% | 1,107,778 | 2.88 秒 |
| Jev 0.7 | 17/20（85%） | 43 / 419 | 9.31% | 1,022,708 | 2.99 秒 |

这批结果显示，原路由器在该开发集上卸载很多，但成功率明显偏低；Jev 0.8 的成功率最高，但几乎总是选择 LLM，不能说它已经证明了“有效卸载”。Jev 0.7 增加了 SLM 使用，也出现了更多失败。

失败轨迹分析发现，Jev 0.7 的 3 个失败中，2 个任务的主要业务检查已通过，但最终 `complete_task(answer=...)` 内容与 AppWorld 期望答案不一致；另 1 个达到 40 步上限，原生 LLM 在该任务也触及步数上限。守卫通过只说明操作满足守卫规则，不等于任务评测成功。这里没有证据支持把收尾答案改成固定值；模型应依据任务生成收尾答案，相关收尾行为若要改，应单独设计对照实验。

对原路由器的失败轨迹检查没有发现 embedding 请求失败或缺向量导致的拒绝；失败主要体现在具体任务执行和评测结果上。因此不能简单把该组低成功率归结为 embedding 服务故障。

## 四、20 个开发任务：四档 Jev 阈值扫描

这次使用 context 模式、同一批 20 个任务，保持 Agent、SLM/LLM 服务和执行守卫流程一致，仅改变 Jev 阈值。80 个任务格全部完成并通过记录完整性检查。

| Jev 阈值 | 任务成功 | SLM / LLM 调用 | SLM 占比 | 已知 Jev 输入 token | 执行模型 token | 加 Jev 输入后的观测 token 增幅 | Jev 平均客户端耗时/任务 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 0.55 | 12/20（60%） | 162 / 299 | 35.14% | 1,032,550 | 6,347,170 | 16.27% | 2.58 秒 |
| 0.60 | 14/20（70%） | 107 / 360 | 22.91% | 1,026,867 | 7,039,757 | 14.59% | 2.61 秒 |
| 0.65 | 12/20（60%） | 94 / 353 | 21.03% | 1,008,580 | 7,283,547 | 13.85% | 2.78 秒 |
| 0.75 | 19/20（95%） | 22 / 446 | 4.70% | 1,098,710 | 8,552,494 | 12.85% | 2.90 秒 |

`token 增幅` 的分母是执行模型 token，只加了有记录的 Jev 输入 token；不等于货币开销增幅。该表显示提高阈值会减少 SLM 调用，但任务成功率并非随阈值单调变化。0.75 当前表现为较少卸载且成功率接近原生 LLM；0.8 的另一批 20 任务结果为 20/20、3 次 SLM 调用。两者是在小开发集上的候选配置，不足以选出最终生产阈值。

### 0.60 与 0.65 为什么会反直觉

逐任务配对：两组都成功 9 个；只有 0.60 成功 5 个；只有 0.65 成功 3 个；两组都失败 3 个。差距是 20 个任务中的 2 个，不足以证明 0.60 普遍更好。

轨迹中能看到几类原因：

- 某些分支由 SLM 生成了不同质量的操作代码，例如 CSV 表头处理、习惯记录字段填写、给邮件收件人范围过宽。
- 有的任务业务操作已完成，但最终答案字段与评测契约不符；有的任务到步数上限前没有调用结束工具。
- 某些阈值选择了不同模型后，后续代码、工具反馈、上下文长度和下一次 Jev 输入都改变了。阈值只在输入与分数完全相同时保证单次决策集合的嵌套关系；在线运行时，整条轨迹不再相同。

因此不能把一次 0.60 的成功简单解释为“0.60 选中了一个固定且正确的 SLM 子集”，也不能把 0.65 的失败全部归咎于阈值本身。

## 综合反馈与建议

1. **先确定评价目标。** 若目标是任务成功率，要做同一任务集、同一服务版本下的原生 LLM、原路由、Jev 对照；若目标是卸载能力，还需要可靠的 Span 级局部正确性/净节省标签。两种评价不能只靠一个平均 P(SLM) 代替。
2. **把 0.75 和 0.8 作为后续候选，而不是结论。** 0.75 在当前 20 个任务上卸载更多且成功率为 19/20；0.8 更保守，成功率为 20/20 但几乎不卸载。先在独立任务集上复测，并重复运行以观察波动。
3. **单独解决 Jev 覆盖率。** 90 任务的长输入不可用较突出。可以在不改变原始审计数据的前提下，评估有 token 预算的上下文摘要/截断策略；每种输入版本要独立记录并重新测量，不能把不可用输入默认为 Jev 已判断正确。
4. **保留失败类别，而不是只看成功率。** 至少分别统计业务断言失败、结束答案不符、步数/上下文上限、Jev 输入不可用、请求错误、守卫拒绝、rollback 和 fallback。它们对应不同修复方向。
5. **在讨论“省钱/省时”前补齐成本口径。** 记录 Jev 输入和输出 usage、未返回 usage 的失败请求、LLM/SLM 各自 token 与服务价格，并使用相同服务负载和配置做配对比较。
6. **避免用这 20 个开发任务反复调参后再宣称泛化。** 这批数据已经参与比较和错误分析，应保留为开发集；最终阈值需要另一个未参与调参的独立任务集验证。
