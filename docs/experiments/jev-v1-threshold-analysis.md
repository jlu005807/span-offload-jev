# Jev V1 阈值结果汇总分析

**整理日期：** 2026-11-01  
**实验范围：** V1 阈值 `0.50`、`0.60`、`0.70`，每组 33 个正式任务  
**数据来源：** 集群运行目录中的 `report.json`、`results.json`、`manifest.json` 和配置快照

## 摘要

在这批 33 个开发/验证任务上，阈值从 0.50 提高到 0.70 时，任务成功率从 **60.6%（20/33）** 上升到 **81.8%（27/33）**。T70 的平均端到端时间最低，但模型执行费用估算最高。T50 的模型执行费用估算最低，成功率也最低；T60 处于两者之间。

目前最稳妥的结论是：**这批结果呈现出更高阈值对应更高成功率、更少 SLM 调用倾向的趋势，但还不足以证明普遍因果关系或选出最终阈值。** 三组均为 `development_experiment=true`、`holdout_evaluation=false`，样本只有 33 个任务；T70 另有一项消费遥测不完整，调用比例及成本只能按下界处理。

## 指标对照

| Jev 阈值 | 成功 | 失败构成 | 成功率（Wilson 95% CI） | 实际 SLM 调用占比 | 端到端时间/任务（均值 / 中位数） | 模型执行费用估算/任务 |
|---:|---:|---|---:|---:|---:|---:|
| 0.50 | 20/33 | 13 evaluation_failed | 60.6%（43.7–75.3%） | 64.7% | 204.2 / 147.3 秒 | $0.0514 |
| 0.60 | 22/33 | 11 evaluation_failed | 66.7%（49.6–80.2%） | 49.7% | 190.6 / 167.5 秒 | $0.0628 |
| 0.70 | 27/33 | 5 evaluation_failed、1 task_timeout | 81.8%（65.6–91.4%） | 不完整；观测调用中 SLM 为 26.4% | 152.5 / 150.6 秒 | $0.0936，下界 |

**卸载率口径：** 实际派发给 SLM 的模型调用数 / 实际派发给 SLM 与 LLM 的模型调用总数，即 `small_model / (small_model + large_model)`。它使用运行时真实派发计数，不是 Jev 的路由概率、建议路由或任务占比。T50 为 `439 / (439 + 240) = 64.7%`；T60 为 `332 / (332 + 336) = 49.7%`。T70 的 `162 / (162 + 452) = 26.4%` 只是已观测调用中的 SLM 比例，不是完整的实际卸载率，不能与前两组的正式 `actual_slm_rate` 等同解读。

端到端时间按每组报告中的 `wall_clock_ms / 33` 计算。模型执行费用按 `estimated_execution_cost_usd / 33` 计算；它不是账单金额，也不含 Jev 服务成本。

Wilson 区间只描述 33 项样本下成功率估计的不确定性，不应视作覆盖未知任务分布的保证。区间明显重叠；比较同一任务集时还应看配对结果，而不能只比较独立比例。

## 资源与遥测

| 阈值 | SLM / LLM 调用数 | 执行模型输入+输出 token | 消费遥测 | 无效测量任务 |
|---:|---:|---:|---|---:|
| 0.50 | 439 / 240 | 7,434,601 | 完整 | 0 |
| 0.60 | 332 / 336 | 7,963,893 | 完整 | 0 |
| 0.70 | 162 / 452 | 9,705,255（下界） | 不完整，`consumption_complete=false` | 1 |

较高阈值下，观测到的 SLM 调用数逐步减少、LLM 调用数增加；成功率也随之增加。T50 到 T60 的 SLM 调用占比下降约 **15.0 个百分点**，同时成功率增加 **6.1 个百分点**。T70 的消费数据不完整，因此其调用结构、token 和成本都可能低估，关于“卸载比例”的定量结论应暂缓。

报告中的 `complete=true` 表示 33 个任务单元均有正式结果，不代表所有 token/调用消费遥测均完整。尤其 T70 的一次任务超时导致消费总量被明确标记为下界。

**T70 的卸载调用记录和完整性：** 任务最终失败/超时，不应抹掉此前已实际完成的模型调用。汇总中 SLM 162 次、LLM 452 次包含超时任务 `fb05fed_3` 的 SLM 9 次、LLM 22 次；它们来自 `partial-execution.json` 检查点，并非被排除。因此可以报告**已完成并返回结果的模型调用中，SLM 占比为 26.4% (`162 / 614`)**。但这不等于已证明所有实际派发都被计数：当前 `GatewayMeter.complete` 在底层模型请求返回后才把调用追加到计数器，超时中断时尚未返回的请求可能不会出现在检查点里。另一个 `consumption_complete=false` 还意味着 token 消费账目不完整。汇总器遇到任一超时或不完整消费便统一将 `actual_slm_rate` 设为 `null`，这是保守的完整性门控；它没有分开表示“已完成调用比例”和“包括未返回派发在内的完整实际卸载率”。因此本报告保留 26.4% 作为有明确分母的已观测 completed-call 比例，同时将完整实际卸载率标为**未能确认**，而不是说没有卸载记录。

## 结果解读

1. **成功率趋势清晰但仍属小样本观察。** T50、T60、T70 分别成功 20、22、27 项。T70 比 T50 多成功 7 项（+21.2 个百分点），但仅 33 个样本，且这是开发/验证集，不应外推为线上成功率。
2. **高阈值的成本代价明显。** 已记录的模型执行费用估算从 T50 的约 $1.70/组升至 T70 的约 $3.09/组。T70 约比 T50 高 82%；由于 T70 遥测不完整，实际差距可能更大。该估算按 `openrouter-2026-10` 列表价、未计缓存折扣，排除 Jev 服务成本；manifest 中 `fee_model=null`、精确 `cost=null`，因此不应称为完整系统成本。
3. **端到端时间与成功率在这批数据中同向改善。** 每任务均值从 T50 的 204.2 秒降至 T70 的 152.5 秒。该时间是 33 个运行记录的汇总均值，受到任务组成、共享服务和单次运行波动影响，不是延迟保证。
4. **当前不能断言单调性或统计显著性。** 成功数只以 2 项、5 项的增量变化，缺少重复运行、置信区间和独立 holdout 验证。T70 还有 1 项无效测量及消费不完整，进一步限制资源效率比较。

## 可比性与限制

- **作业与产物状态：** T50/T60 来自 `569668` 的两个阈值子目录；该 Slurm 作业整体后来达到时限，但 T50/T60 各自的 report、results、progress 均为 33 条，`complete=true`、`consumption_complete=true`，acceptance 为 `ready_for_batch=true`。旧 T70 子目录不作为本报告的 T70 数据；T70 使用独立重跑作业 `573055`，Slurm `COMPLETED`，用时 2:03:21，其 report/results/progress 均有 33 条且 acceptance 为 ready，但 `consumption_complete=false`、有 1 项无效测量。
- 三份 manifest 的正式 `task_ids` 都为 33 项，任务 ID 列表 SHA-256 均为 `6df01b12db6973d31c239f016363e9076d03cd1365b629ef6f36e7383b8a2d69`；三组使用相同的 V1 prompt 版本及哈希 `a520f9c99e990a6ce282dbcf29d5347ff085685953c86e394dfc1f3f21362b2a`。
- T50/T60 使用提交 `04e867f`，T70 重跑使用 `8e4fe5b`。服务器 Git diff 涉及批处理支持显式选择阈值、Smoke 任务可独立指定及相关验收/测试变更；未见正式路由决策逻辑变化。T70 的 Smoke 使用独立任务且不计入正式结果。
- 三组各自保存了配置快照，文件中阈值分别为 0.50、0.60、0.70。集群连接在最后一次逐字段配置对比前中断，因此本报告不把“阈值以外的配置完全相同”当作已验证事实；复现或正式选型前应再校验三份配置快照。
- 三组都是 `development_experiment=true`、`holdout_evaluation=false`。这里的“完整”仅表示每组 33 项均已完成记账，不等于独立测试集结论。
- 三组报告中的模型调用费用是模型执行费用估算，缺少 Jev 推理服务成本、GPU/服务运行成本和可能的其他基础设施费用。

## 阈值选择建议

如果当前阶段优先追求这批任务的成功率，T70 是本轮表现最好的候选；如果更重视模型调用成本，T50 更省但成功率较低。T60 暂时没有显示明显的帕累托优势：相较 T50 成功率只提高 6.1 个百分点、费用估算提高约 22%，而 T70 的成功率提升更明显但成本更高且遥测不完整。

因此建议把 T50/T60/T70 保留为**候选策略**，而不是宣布最终阈值。下一步应在独立 holdout 上按同一任务集复测候选阈值，并确保所有组消费遥测完整；同时把 Jev 服务成本纳入成本模型，再按成功率、延迟和完整系统成本共同决策。

## 后续 V1/V2/V3 提示词版本比较口径

用户目标同时重视**较高成功率**和**较高实际卸载率**，这两个指标可能相互牵制，建议先报告二维结果，不先合成一个未经约定的总分。版本 X 只有在成功率和实际卸载率均不低于版本 Y、且至少一项更高时，才可称为支配 Y；若一项更高、另一项更低，则应保留为质量/卸载的权衡候选。

后续版本比较应固定或逐项记录以下条件：

1. 使用相同的 33 个正式任务 ID、AppWorld 数据版本、运行模式、阈值和运行器配置；若目的是“提示词版本效应”，提示词内容/哈希应是唯一有意变化项。
2. 固定并记录 LLM/SLM 服务模型 ID、模型 revision、服务端配置和价格表版本。若服务在不同时段运行，记录时段与 endpoint，避免把服务漂移当成提示词收益。
3. 每个版本用 `framework_model_calls_by_target` 计算实际卸载率；同时报告分子、分母和任务数。缺计数、超时或消费不完整时应报 `null`/不完整，不用 JEV 概率或观测下界替代完整卸载率。
4. 成功率按 `task_success=true` 的任务数除以正式任务数；另列失败类别和 `valid_for_comparison`。任务结果完整与遥测完整分别核验。
5. 对相同任务做配对比较，报告每组成功、失败、双方一致与单边胜出的任务数；成本、延迟报告均值和中位数，避免只看总体均值。
6. 先在当前开发/验证集筛选 Pareto 候选，再在未用于调参的独立 holdout 上复核。最终版本应按预先写明的最低成功率与最低卸载率要求选择；若暂无硬性门槛，则交付 Pareto 前沿供决策。

按当前 V1 结果，T50 是卸载率最高的候选（64.7%），T70 是成功率最高的候选（81.8%，但该组实际卸载率未完整计算）；因此 V1 目前没有一个可由本报告证明能同时达到“高成功率、高卸载率”的已验证配置。V2/V3 的比较应沿用上述定义，不把“提示词偏向 SLM”视为卸载率证据，必须看真实派发统计。
